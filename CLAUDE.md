## What this is

**SafeSpace** is a mental-health / therapy-simulation app. A user picks a therapeutic modality + avatar, then runs a time-limited AI chat "session". Conversations are private by design: the entire architecture is built around a **privacy boundary** that keeps raw conversation content out of logs, admin surfaces, and unbounded context reuse. When in doubt about whether something may touch `session_messages.content`, `session_summaries.summary_text`, prompts, or provider payloads — assume it's privileged and route through the dedicated boundary helpers.

## CI / deploy (`.github/workflows/ci.yml`)

On push/PR to **`main`**, `ci` runs audit → Vitest → disposable PostgreSQL tests → Astro sync → lint → TypeScript → Astro check → production build → Chromium installation → E2E. The test build uses `SUPABASE_URL=https://example.supabase.co` and `SUPABASE_KEY=test-public-key`, matching the isolated E2E preview. It needs no production secrets, including for Dependabot and fork PRs. On push to `main`, a single `deploy` job verifies the commit is still current, builds separately with real Supabase secrets, applies migrations via the Session Pooler, then publishes the Worker. Its `deploy-main` concurrency group (`queue: max`, no cancellation) holds the lock across both migration and publication. Never split them into separately locked jobs. Superseded commits fail before any production mutation. Adding a behavior requires a meaningful test.

## Architecture

Astro 7 SSR (`output: "server"`) + React 19 islands + Tailwind 4 + Supabase auth + shadcn/ui, deployed to Cloudflare Workers (`wrangler.jsonc`, `nodejs_compat`). All pages server-rendered; **API routes must export `const prerender = false`** and use uppercase method exports (`GET`, `POST`).

### Request lifecycle

`src/middleware.ts` runs on every request and:

1. Mints a `requestId` (`context.locals.requestId`) for operational logging and stamps it on the response header, then resolves the UI locale from the `safespace-locale` cookie into `context.locals.locale` (see "Internationalization").
2. Guards `/api/*` request bodies before any parsing (`src/lib/request-guards.ts`, tested there because vitest does not collect `src/*.ts`): oversized → 413 (32 KB default, 7 MB only for `/api/session/transcribe`, WebM audio); a body without a parsable `Content-Length` → 411 `{ code: "length_required" }`, because a chunked upload would otherwise bypass the cap entirely. A request with no body at all passes.
3. Rate-limits the auth form endpoints (POST `/api/auth/signin|signup|reset-password|resend-confirmation|password`) **per IP** via the `AUTH_RATE_LIMITER` binding, before Supabase is even called: the Worker talks to Supabase from shared Cloudflare egress IPs, so Supabase's own per-IP limits are one global bucket for all users. Over-limit → 303 back to the form page with `?error=rate_limited`. This limiter is deliberately **fail-open** everywhere — a broken binding must not lock everyone out of sign-in.
4. Resolves the Supabase user via `createClient()` → `context.locals.user` (cookies carry `Secure` in production builds).
5. Rate-limits AI-backed session endpoints (POST `/api/session/message`, `start`, `start-next`, `prepare-memory`, `prepare-people`, `transcribe`, and `summary/*` by prefix) per user via the Cloudflare `SESSION_RATE_LIMITER` binding (`src/lib/rate-limit.ts`, wrangler.jsonc). Fail-open when the binding is absent (local dev, tests), fail-closed in production; over-limit → 429 `{ code: "rate_limited" }`.
6. For `PROTECTED_ROUTES` (`/dashboard`, `/account`, `/admin`): redirects unauthenticated users to `/auth/signin`, then checks **account access** (`readAccountAccessState`) and redirects blocked/unavailable accounts to `/account/blocked`. Result lands in `context.locals.accountAccess`. The form endpoints outside `/api/session/*` that mutate account state (`/api/profile/avatar`, `/api/auth/password`) apply the same block check themselves.
7. Stamps baseline security headers on every response (X-Frame-Options, HSTS, Referrer-Policy, Permissions-Policy…). **The CSP itself comes from Astro** (`security.csp` in `astro.config.mjs`), built at compile time from the real island/style hashes — the middleware does not set it. Two directives there are load-bearing and easy to break:
   - `form-action` must list every origin the OAuth start redirects through (Supabase project + `accounts.google.com`), because Chrome re-checks it on **each redirect** of a form-triggered navigation — with a bare `'self'` the "Kontynuuj z Google" button dies as a silent `net::ERR_ABORTED`. The Supabase origin is read from `SUPABASE_URL` at build time, so the build needs that variable (CI already provides it).
   - `is:inline` scripts are **not** hashed by Astro; their hashes are computed from `Layout.astro` at build time (`collectInlineScriptHashes`). Without that, the pre-paint theme script is blocked and a saved theme choice stops applying. Both live in `src/lib/security/csp.mjs`, covered by `src/lib/security/__tests__/csp.test.ts`. Note CSP is emitted only in production builds — `astro dev` sends no policy, so CSP regressions are invisible in dev. A production build without a usable `SUPABASE_URL` **fails on purpose** (`assertBuildSupabaseOrigin`) instead of silently shipping a `form-action` that kills Google sign-in; set `SUPABASE_URL=https://example.supabase.co` for a local throwaway build.

Every auth form route reads its body through `readFormData()` (`src/lib/auth-route.ts`), which turns an unparsable body into an empty form and therefore into that route's own validation code — never a 500. Admin mutations validate the target id as a uuid (404 `target_not_found`) and refuse an admin acting on their own account (400 `self_target_forbidden`), because a self-block is a lockout only owner-run SQL can undo.

CSRF: `security.checkOrigin: true` in `astro.config.mjs` (explicit, do not remove) makes Astro reject form-content-type POST/PATCH/PUT/DELETE with a mismatched `Origin` header; JSON requests are covered by the CORS preflight model.

Auth: `src/lib/supabase.ts` (cookie SSR client, `astro:env/server` secrets), pages in `src/pages/auth/`, endpoints in `src/pages/api/auth/` (incl. Google OAuth `google.ts` + `callback.ts`).

### Internationalization

Two locales, `en` | `pl` (`src/lib/i18n/locale.ts`). **The default is always `en`** when nothing is stored — deliberately no `Accept-Language`, no URL prefixes, no Astro `i18n` routing. The flow:

- `src/middleware.ts` reads the `safespace-locale` cookie (httpOnly, lax, one year) into `context.locals.locale` right after `requestId`, before any early return, and stamps `Vary: Cookie` on every response (public pages are not `no-store`, and the same URL renders in the cookie's language — do not remove it). `Layout.astro` takes `<html lang>` and the default description from `Astro.locals.locale`; pages never pass a `lang` prop.
- `POST /api/profile/locale` (`src/pages/api/profile/locale.ts`) is a native form (`LocaleSwitch.astro` in the header, the admin shell and `/account/security`; languages are shown as inline SVG flags from `LocaleFlag.astro` — no emoji, no external images under CSP — with the endonym kept as sr-only text so the button's accessible name stays "Polski" / "English"): it validates the locale and a same-origin `returnTo` (`i18n/return-path.ts`), writes the cookie, upserts `user_preferences` for a signed-in user (fail-open) and 303s back. Deliberately **no** block check (a blocked account must read its page in its language), **no** logging (locale is never an allowed log field) and **no** rate limit (no credentials, AI or Supabase Auth calls; `checkOrigin` covers CSRF). It must keep working signed-out and without Supabase — the E2E preview relies on it.
- `syncLocaleAfterSignIn` (`i18n/account-locale.ts`) runs in `signin.ts`, `signup.ts` (only when a session was created) and `auth/callback.ts`: the account row wins and refreshes the cookie; otherwise an explicit cookie choice is adopted by the account; the implicit default is never persisted. Never blocks sign-in. `user_preferences` is owner-only (RLS, revoke-first column grants, `user_id` pinned by trigger), cascades with the account, and is pinned by `schema-drift.test.ts` and `npm run test:db`.
- **Copy rule: no hard-coded UI strings in JSX/Astro.** Every string — including `title=`, `aria-label`, `placeholder`, `alt`, sr-only text, `<noscript>`, `mailto:` subjects and `<title>` — comes from a `*-copy.ts` module built with `defineCopy(en, pl)` (`i18n/copy.ts`: the type is inferred from `en`, so a missing Polish key is a compile error) and read through `getXCopy(locale)`, `locale` always first. Shared/server copy lives in `src/lib/**`, one component's copy next to it, page copy in `src/lib/page-copy/`. Islands receive `locale` as a prop, wrap their tree in `LocaleProvider` and read it with `useLocale()` — never `navigator.language` or `document.documentElement.lang` (hydration mismatch). Register every module in `src/lib/i18n/__tests__/copy-catalogs.ts`: `copy-parity.test.ts` checks key parity and untranslated English, `polish-copy-diacritics.test.ts` checks the Polish branch. `/privacy` prose lives in per-locale partials (`src/components/privacy/PrivacyContent{En,Pl}.astro`) with neutral section ids.
- `modalities.ts` holds only language-neutral and prompt fields (`avatarFirstName`, `sessionStyleHint`, `summaryLensHint`, per-locale `registerExamples`); names, roles, descriptions and alt text come from `modality-copy.ts` (`getModalityCopy(locale, modalityId)`). `SelectedModalityAvatar` carries no text, so API DTOs stay language-free.
- **AI language pins move together**: `buildSessionResponseSystemPrompt` / `buildSessionOpeningGuidance` / `getSessionOpeningGenerationInstruction` and the voice pair `buildVoiceLiveInstructions` / `buildVoiceBackendInstructions` (session-ai; the live layer's prompt is written in the conversation language because GPT-Live speaks the language of its instructions), `buildSessionSummarySystemPrompt` / `buildAvatarMemorySystemPrompt` (session-summary), the transcription `language`, and `getCrisisSafetyCopy` / `getCrisisResourceRegions` (session-safety) all take the request locale. Routes obtain it only through `getRequestLocale(context.locals)`; flows in `session-flow/*` take `locale` as a parameter and never read `locals`. Prompt metadata uses the English avatar names (`getModalityPromptNames`) regardless of UI language. The cumulative avatar memory may be rewritten in the other language after a switch; stored transcripts keep the language they were written in. Crisis resources always show all three regions with identical numbers — only labels translate.
- Account deletion accepts either locale's confirmation word (`account-deletion.ts`: `DELETE` / `USUWAM`, exact match); the RPC still receives the fixed `USUWAM` contract.

### Session flow (the core feature)

`POST /api/session/message` (`src/pages/api/session/message.ts`) is the canonical orchestration and the file to read first. Order is load-bearing:

1. `getSessionDataContext(context)` — owner-bound private data context (never `.from(...)` private tables directly).
2. `requireActiveAccountAccess` — block check.
3. Load owned session metadata and call `claimSessionMessageTurn` before reading recent messages. The client's UUID plus message hash identifies a retry: a completed receipt replays its pair without calling AI; another in-flight turn returns `message_in_progress`. A two-minute lease serializes generation per session without holding a transaction open during the provider call. Release unfinished leases in `finally`; completion checks the attempt UUID so an abandoned Worker cannot write after a retry takes over. Receipts/hashes are private data, never admin or log fields. Old clients lacking a UUID are accepted during rollout but cannot deduplicate retries.
4. **`evaluateSessionSafety()` gates everything.** Branch on `decision.action`, never on model output: `allow` → normal generation; `allow_with_constraints` → pass `decision.constraints` to the model (no user-visible warning); `hard_stop` with a detected-crisis reason code → interrupt the session, return `decision.copy` + `decision.crisisResources` (HTTP 423). Missing selected AI provider config, timeout, or a malformed provider reply also come back as `hard_stop`, but with a **fail-closed reason code** (`isFailClosedSessionSafetyReasonCode`, `session-safety/reason-codes.ts`): the turn is refused as a retryable `ai_retry` 503 with `getSafetyBoundaryUnavailableCopy()` and the session keeps its status. `interrupted` has no way back and counts against the free-plan cap, so a provider blip must never end a conversation. The classifier gets the user's own last two turns as bounded context (`recentUserMessages`) and is told the text is untrusted; it runs in parallel with the continuity-context read (nothing is generated or stored before the decision). One fast provider failure (5xx/429) is retried once; a timeout is not.
5. Enforce the per-session time budget (`session-flow/time-limit`); expired → 409. The provider timeout for one reply is `getProviderTimeoutWithinSessionMs(session, now, ceiling)`: the ceiling follows the configured reasoning effort (`resolveSessionReasoningTimeoutMs`: 12 s, `high` 30 s, `xhigh` 60 s) and the remaining session time minus a reserve always wins when shorter. Do not reintroduce a fixed 12 s cap on the route — with `xhigh` it aborted most turns and still billed the reasoning.
6. `generateSessionResponse()` with recent messages + **the pinned automatic avatar memory** for new follow-ups (`usesAvatarMemory`). `session-flow/session-continuity.ts` reads the session copy from `avatar_session_contexts`; it never sends raw prior transcripts to reply generation. Legacy sessions keep their original `usesApprovedContext` decision and approved summaries, scoped to the session avatar. How many recent turns are read scales with the session's own budget (`session-flow/context-window.ts`: 8 for 15 min, 20 for the premium hour; the prompt builder caps at 24). Summaries are model-generated text that reaches later sessions inside the system role, so the prompt fences each one between `<<<summary>>>` / `<<<end summary>>>` markers, strips any marker-like text from the note itself, and states that the fenced text is data, never instructions. The reply is also shaped by `resolveSessionPhase()` (`session-flow/session-phase`), which maps the session's remaining budget to `opening | middle | closing`. Thresholds are **fractions of this session's own budget** (capped in absolute time), so the arc holds for the 15-minute trial and for longer paid sessions alike — never add fixed minute marks. Only the phase label reaches the model, never the remaining time.
7. Re-read the session status, then call `persistSuccessfulMessageTurn` (never direct inserts). Its `complete_session_message_turn` RPC is the final gate: under a session row lock it checks ownership, status, expiry and lease, allocates sequence indexes, and writes both messages and the receipt atomically. A concurrent end/deletion cannot slip between checking and writing. Log `session.ai_turn_completed` with the provider's `inputUnits` / `outputUnits` only for a freshly completed turn, not a replay.

Other session routes: `start.ts` / `start-next.ts` (start free trial / automatic avatar-memory follow-up), `end.ts` (explicit completion / expiry transition via `session-flow/session-completion-contract`), `transcribe.ts` (voice input → text), `history/`, `summary/`. Avatar choice is saved via `POST /api/profile/avatar` (redirect-based errors from `avatar-choice-errors.ts`).

### Automatic avatar memory

`POST /api/session/prepare-memory` calls `prepareOwnedAvatarMemory` in the background while the dashboard or a finished-session screen is open. It checks owner access, quota and the session rate limiter, and never creates a session. `useAvatarMemoryPreparation` shares in-flight batches within the browser tab and stops on the first failure or unmount; an explicit start waits for its current batch to save. This is opportunistic preparation, not a durable background queue. `POST /api/session/start-next` finishes any remaining work before creating a session or starting its clock. Each request summarizes up to 48,000 Unicode source characters across multiple eligible conversations, with a separate 128-message cap for metadata overhead. `get_avatar_memory_batch` bounds content in the database and reads only unprocessed history in chronological order; oversized messages resume at their absolute Unicode cursor. The prompt receives local conversation ordinals, never source IDs. `save_avatar_memory_batch` atomically saves the aggregate and all source cursors; the old RPCs remain compatible through shared cursors and revision fencing. A post-save completeness read avoids another start request for the last batch. The route returns 202 while work remains, and `useSessionStart` resumes until it receives the session. All eligible conversations are traversed, not just the newest three or the last 40 messages. A failed provider call preserves every cursor and returns a retryable error.

Opening messages use `low` reasoning by default to keep session starts responsive. Conversation replies still use `OPENROUTER_SESSION_REASONING_EFFORT`; the opening retains the same pinned avatar memory and privacy boundaries.

### People cards ("Osoby z Twoich rozmów")

Owner-private, per user + avatar notes about the people the user mentions, behind `PEOPLE_MEMORY_MODE` (`off|on`, public server env; `wrangler.jsonc` has it `on` since 2026-09-06 — flip it to `off` to stop creating and using cards without losing saved ones). `src/lib/session-data/people-memory.md` is the authoritative contract. The load-bearing rules:

- **Identity is the UUID, never the name**: two people called Marta are two rows; extraction disambiguates by relation and creates a new person when unsure. Facts are small, independent rows (`who | account | feeling | wish | attempt | outcome`, ≤200 chars) with a **set of source conversations**; deleting any source conversation deletes the fact. Prompts receive local refs only, never database ids. `attempt` (something the user explicitly agreed to try) and `outcome` (what the user later said came of it) are the timeline: an outcome never replaces an attempt, the dialog shows both chronologically under one heading, the brief ranks them right after `who` (five entries per person, `feeling` yields first), and the reply prompt may ask lightly how an attempt without an outcome went — never as an opening question.
- **Separate pipeline**: `POST /api/session/prepare-people` (`session-flow/people-memory.ts`) has its own cursors and revision; the client runs it after the memory loop and **a session start never waits for it**. An overflowing model response (`incomplete`) halves the batch without moving cursors. `save_people_memory_batch` returns `false` only for races, raises `22023` for contract violations and silently skips semantic overflows so the client cannot poll forever.
- **User corrections win**: an edited name/relation is locked and a corrected fact is `user_edited`; the model cannot overwrite them and every edit bumps the revision so an in-flight batch loses its CAS.
- **Forgetting is durable and wide**: `forget_person` records a `(name, relation)` exclusion, invalidates the avatar memory like a conversation deletion (the rebuild prompt receives `forgottenPeople`) and re-renders pinned briefs. Switching off blanks pinned briefs; switching back on fast-forwards cursors ("from now on"). Managing saved cards (forget, delete entry, "switch off and delete all") works regardless of the flag; only creation and use are gated.
- **Prompt**: `loadOwnedSessionContinuity` returns `peopleBrief` from the same pinned copy as the memory; the section sits after the avatar memory, fenced with `<<<people>>>` markers, and states that notes are the user's perception, never facts about absent people. `aboutPersonId` in the start body pins that card first in the brief and `session.astro` prefills the composer (name and relation, never in the URL).
- **Logs**: `session.people_memory_updated` carries outcome, duration and unit counters only; names, counts and ids never reach logs or admin.

### Topic map ("Mapa tematów")

Owner-private difficulties the user says they struggle with, the people those difficulties come up with, and the ways of coping that came up in conversations, behind `TOPIC_MAP_MODE` (`off|on`, public server env, read only through `session-flow/topic-map-mode.ts`; `wrangler.jsonc` has it `on` since 2026-09-12 — flip it to `off` to stop extracting difficulties and using the brief without losing saved cards; all four stages of the plan are deployed: data and extraction, list and dialog with settings, the SVG graph, and the reply-prompt brief). `src/lib/session-data/topic-map.md` is the authoritative contract. The load-bearing rules:

- **Same pipeline as people cards, never a third pass**: `POST /api/session/prepare-people` runs when either flag is on; one batch, the shared cursors `people_memory_sources` and the shared revision `people_memories.revision`. `get_people_memory_batch` returns `enabled` (cards) and `topicsEnabled` (map) and messages while either preference is on; each part is active only when its flag **and** preference are on, and `save_people_memory_batch` applies each part only under its preference (both off → `false`). The prompt receives a difficulties index with local refs beside the persons index; a difficulty may link a person created in the same response by `newPersonPosition`.
- **A difficulty belongs to the user, a person is an edge**: `difficulties` (label ≤60 without names or diagnoses, `label_locked`, `archived_at` set only by the user), `difficulty_persons` (`suggested | confirmed | rejected`, `user_decided` untouchable by the model, `rejected` blocks re-adding), `difficulty_entries` (`how | coping | update | suggested | agreed | outcome`, optional `person_id` behind an edge, `effect ∈ better | same | worse | resolved | mixed` only on `update`/`outcome`, `parent_entry_id` with the pairs `agreed→suggested`, `outcome→agreed`, `outcome→suggested`, `on delete set null`), per-entry source sets and mentions. "Current state" is the latest `update` by source-conversation date; `update` has a rolling window of 6 outside the 12-entry cap.
- **Deduplication in three layers**: the prompt is merge-first for difficulties (the opposite of people, where privacy wins), the SQL folds a new difficulty whose normalized label or own alias matches an existing label or alias into that row (`difficulty_aliases` unique per perspective, ≤6), and `merge_difficulties` lets the user join two rows without losing data (caps are not enforced on merge). A rename onto a taken label raises `P0014` → `duplicate_difficulty_label`; the old label becomes an alias.
- **Coercion, never a failed batch**: a bad parent pair, an `effect` on the wrong kind, an entry at a person without an edge, an unknown ref or position is dropped or nulled in the parser and again in SQL; `replaceEntries` updates in place so children keep their parent. Suggestions are the one exception to "a suggestion is never a fact": `suggested` records the avatar's proposal as a proposal.
- **UI mirrors people cards, one section lower**: `TopicMap` (`src/components/topics/`) sits under the people section on `/dashboard` behind its own flag and preference; the list shows no entry text, a "to confirm" bar asks only about uncertain person links, and the native dialog holds the timelines (`update` effects; `suggested`/`agreed`/`outcome` by source-conversation date with the answered proposal named), person decisions, rename/note/"less current", entry corrections, "merge with…" (a taken name offers the local match) and the archive nudge after a `resolved` state. Owner routes live under `/api/session/topics/*` (contract `session-flow/topic-map-contract.ts`, `duplicate_difficulty_label` → 409); list, card edit, person decision and merge are flag-gated, deletions and entry corrections are not. `aboutDifficultyId` in the start body (`?topic=` in the address, never the label) is validated like `aboutPersonId` and stored on the session; the settings card and the privacy partials follow the people-cards pattern under `#topic-map`.
- **The graph is a second view of the same cards, never a separate data path**: `src/lib/topic-map/layout.ts` is a pure, deterministic layout (you in the middle, difficulties on a ring sorted like the list, linked people on the outer ring at the circular mean of their difficulties' angles, spread so 30 difficulties and 40 people never overlap); `TopicGraph.tsx` renders it as plain SVG with theme tokens only (clay stays reserved for crisis help, so a link to confirm is a dashed `ink-muted` line), every node is a `<g role="button">` with keyboard navigation, a difficulty node opens the shared dialog, a person node highlights its topics. The "Map / List" switch renders the list on the server, then the remembered choice or the width default (map from 768 px) through `topic-map-view.ts`; the map scrolls inside its own container, never the page.
- **Prompt**: `loadOwnedSessionContinuity` returns `topicBrief` from the same pinned copy as the memory and the people brief (`avatar_session_contexts.topic_brief_text`, ≤3000, `20260907100000_add_topic_brief.sql`), only while `TOPIC_MAP_MODE` is on; the section sits after the people section, fenced with `<<<topics>>>` markers, and states that the notes are the user's account and never a diagnosis or a plan. Load-bearing rules: a strategy the user said made things worse is never proposed again, one that helped may be built on in the user's words, a resolved difficulty is not reopened unprompted, a decision without "how it went" may be asked about lightly when the topic returns but never as the opener, and `aboutDifficultyId` pins that difficulty first. `private.render_topic_brief` uses only confirmed person links and difficulties not marked less current; every user correction, merge, forget and conversation deletion refreshes pinned briefs (`private.refresh_topic_briefs`), switching the map off blanks them, and a batch save never touches them.
- **Deletion contract mirrors people cards**: a deleted conversation removes what it sourced, forgetting a person drops their edges and entries (general difficulties stay), "delete all people cards" keeps general difficulties and the aggregate row only for perspectives that hold difficulties, "delete the map" leaves people alone; user edits bump the revision so an in-flight batch loses its CAS. Labels, aliases, entries, counts and ids never reach logs or admin.

### Thematic lenses (soczewki tematyczne)

"One attending clinician and a bench of specialists" without switching model or avatar: when a conversation clearly circles one theme, the reply prompt gets a ≤600-character module of **what to listen for and what to ask**, appended inside the modality section. `src/lib/session-lens/README.md` is the contract; the catalog (`SESSION_LENS_IDS`: `family_of_origin | work_burnout | anxiety_avoidance`) lives in `session-ai/session-lenses.ts` because it is prompt material. Behind `SESSION_LENS_MODE` (`off|on`; `wrangler.jsonc` has it `on` since 2026-09-06). Load-bearing rules: detection is a **separate cheap call** (`detectSessionLens`, safety model, strict `{ lens }` schema, 6 s, no retry) run in `Promise.all` beside the safety classifier only while the session has no lens — never an extension of the safety classifier, whose closed parser is fail-closed; the lens is **fail-open** by contract (any failure = a reply without a lens, never a refused turn). The first detected label is **sticky for the session** (`therapy_sessions.session_lens`, `setOwnedSessionLens`: owner, active, column still null; `none` is not stored so the next turn tries again). The label says what the conversation is about, so it never reaches logs (`session.lens_evaluated` carries result, duration, provider and unit counters only), the client session view or admin aggregates. A module is written as "listen for / ask", never "act as" — Iga's `Avoid:` forbids switching techniques every message. The builder is part of `deployed-model-budgets.test.ts`.

The 6000-character cumulative summary lives in owner/ avatar-scoped `avatar_memories`; `avatar_memory_sources` stores per-conversation progress. An insert trigger atomically checks completeness and pins a private copy in `avatar_session_contexts`. A revision UUID fences concurrent saves and deletion. Deleting a source clears the avatar aggregate, progress and pinned copies; the next start rebuilds from remaining conversations. See `src/lib/session-data/avatar-memory.md` for the full contract. No extra environment variables or services are required; the additive migration must precede the new Worker.

### Account plans and the free-plan session limit

Accounts are `free` or `premium` (`AccountPlan` in `session-data/types.ts`). Effective premium is a manual grant (`admin_user_profiles.premium_granted_at is not null`) OR a confirmed paid billing period (`billing_entitlements.paid_until > now()`). The shared SQL rule uses database time; application reads, admin plan filters and session gates use that same result. **A free account may own at most `FREE_PLAN_SESSION_LIMIT` (3) sessions in total** — every `therapy_sessions` row it owns counts, any lifecycle status, deleted tombstones included, so deleting never frees a slot; premium accounts are not capped. The first session is still the one-per-user free-trial claim; sessions 2–3 are ordinary follow-ups — the cap is orthogonal to the start/start-next split and applies to both routes.

**The plan also sets the length of a single conversation**: free 15 min, premium 60 min (`FREE_TRIAL_DURATION_SECONDS` / `PREMIUM_SESSION_DURATION_SECONDS`, resolved by `resolveSessionDurationSeconds()` in `session-flow/session-budget.ts`). Both start routes pin it at start from the plan they already read for the quota, so a grant or revoke mid-conversation never stretches or cuts a session under way; everything downstream (timer, `resolveSessionPhase()`, expiry) derives from that session's own `expires_at`. Because a premium account's _first_ session is still the trial claim, the DB side had to admit both budgets: `therapy_sessions_trial_duration_check` allows `(900, 3600)` and `claim_free_trial_session()` takes `p_duration_bucket_seconds` (default 900) and rejects anything else. `schema-drift.test.ts` pins the constraint, the function guard and the TS constants together.

- **The gate is the database**: BEFORE INSERT trigger `therapy_sessions_enforce_free_plan_limit` (per-user advisory lock + count) raises SQLSTATE `P0005` / `free_plan_session_limit_reached`, mapped by `session-data/errors.ts` to the stable `session_limit_reached` code (`FREE_PLAN_SESSION_LIMIT_SQLSTATE`). It fires for the trial-claim RPC and for direct owner inserts alike, so a client talking to PostgREST directly cannot bypass it.
- **Pre-flight, not enforcement**: `readSessionQuota()` (`session-data/quota.ts`: own plan row + `countOwnedSessions`) feeds `readSessionStartPageState()` → kind `session_limit_reached` (no start offered, `sessionQuota` carried in every start state for the remaining-sessions copy) and the early 403 `session_limit_reached` in `start.ts` / `start-next.ts` (redirect `/dashboard?start=limit_reached`). A race-time DB rejection maps to the same 403. Do not re-implement the cap in the UI or count per route.
- `schema-drift.test.ts` pins `FREE_PLAN_SESSION_LIMIT` and the SQLSTATE to the limit migration — change both sides together.
- Manual premium is granted/revoked by an active admin (`POST /api/admin/users/[userId]/plan`, audited as `premium_granted` / `premium_revoked`) or by owner-run SQL. The table action follows `premiumGrantedAt`, while its badge and plan filter follow effective premium; admin clicks do not cancel or confirm a Stripe subscription. `AccountAccessState` (middleware, `requireActiveAccountAccess`) carries `plan` for convenience, but session routes read the plan through `readSessionQuota()`.

### Stripe Managed Payments: local sandbox only

`src/lib/billing/README.md` is the billing boundary and local-testing contract. `BILLING_MODE` defaults to `off`; `sandbox` accepts only test keys. One subscription costs PLN 49 gross monthly. Hosted Checkout uses `mode=subscription` with Managed Payments explicitly enabled. Portal allows payment-method updates, documents and cancellation at period end. There is no standard-checkout fallback when Managed Payments is unavailable.

User POST routes `/api/billing/checkout` and `/portal` require authentication, same origin and `BILLING_RATE_LIMITER`. Checkout also requires an active account; blocked owners retain portal and account-deletion access. `/account/billing` and `GET /api/billing/status` read owner-only RLS projection `billing_status`; they do not expose Stripe IDs. A success URL only starts polling and never grants premium.

`POST /api/billing/webhook` bypasses Supabase Auth and the normal body guard, verifies a signature on raw bytes with Workers-compatible async crypto, and enforces its own 256 KiB streaming cap, including absent `Content-Length`. While billing is off it returns 503 before reading the body. Stripe state is re-read under a per-owner lock before transactional reconciliation and event deduplication. Only confirmed payment for the configured price extends paid access; failed renewal never creates grace days. Unchanged manual premium stays independent.

Billing writes use `pg` with login `safespace_billing_login` inheriting only `safespace_billing`, restricted to billing tables/functions. The Worker never receives `service_role` or a PostgreSQL owner credential. No billing payloads, credentials or customer details enter logs. Keep new billing SQL compatible with the deployed code and apply its additive migration before the code that reads the new views.

For local sandbox verification, build first and run `npm run dev:billing`, which reads ignored `.dev.vars.billing` and serves `http://127.0.0.1:4321`. Its temporary workerd config loads sandbox settings separately from the production defaults. This does not change production settings: `wrangler.jsonc` keeps billing off and provider-dependent secrets validated before deployment. Production payment activation and its deployment configuration are separate work.

### Where each screen starts and ends

The UI deliberately keeps one job per view; splitting a step across two pages is what the navigation audit removed, so re-adding a "prepare to start" screen is a regression, not a feature:

- **`/dashboard`** owns starting a conversation (`SessionStartCard` → `useSessionStart` → start/start-next, then redirect to the session page), the saved-avatar card, and the **only** conversation history in the app. History is stored per avatar, so the section names the perspective and offers a switcher (labelled avatar buttons, `?historyAvatar=<avatarId>`, distinct from the `?avatar=updated` save flash). Keep the filter mounted when changing avatar/page; only the data subtree resets, so native arrow-key navigation retains focus. The switcher lists only perspectives that have conversations (plus the saved one and the one in the URL), each with its count from `countOwnedSessionsByAvatar` (aggregate, no content); with one perspective there is no switcher, and a failed count read falls back to all five. The list groups rows under day headings (`groupSessionHistoryItemsByDay`) and carries **one** action per row, and **the whole row is that button** (time, duration and badges sit inside it; a bare chevron at the row's end was the only tappable thing on a phone) — it opens the read-only preview in a native modal dialog (Escape closes it and restores focus to its row); **deleting lives inside that preview**, never on the bare list, because rows differ only by time and deleting what you cannot see is how the wrong conversation goes. There is no status legend: badges explain themselves and carry the description in `title`. A row may carry a summary marker (`summaryState`, see `session-data/` below): state only, never a word of the summary itself. On a phone the source order is start card → history → help block, so a returning reader does not scroll past the crisis block to reach yesterday's conversation. The help block, the landing's boundaries section and the privacy page render the crisis numbers from `getCrisisResourceRegions(locale)` (all three regions, labels in the request language; `CrisisRegionList.astro` lays them out by container width) — never as literals in a template, and never the Polish region alone: an English UI used to show only Polish helplines, and `crisis-resources.test.ts` now scans `src/` for hard-coded numbers.
- **`/dashboard/session`** is the live conversation only. Without a session (`readSessionStartPageState().session === null`) it redirects to `/dashboard` — the page never renders a start button. While a reply is in flight the composer is `readOnly` + `aria-busy`, never `disabled` (a disabled textarea drops keyboard focus after every turn); "Zakończ rozmowę" ("Zakończ" on a phone, a word and never an icon) stays available, since the route re-checks the status before persisting; after 12 s a "trwa dłużej niż zwykle" status appears and the client gives up at 80 s (`api-client.ts` `timeoutMs`) with the draft restored. A message that was in flight when the session expired, or a draft left when it ended, is shown on the closing card as unsent text with a copy button — never after a crisis hard stop. The timer applies a server clock offset computed from the server's own remaining seconds, so a skewed device clock cannot end the session early. `missing_auth` / `account_blocked` mid-session redirect to sign-in / the blocked page instead of offering a retry. Voice input renders the "Dyktuj" button only when the browser can record a supported WebM type (Safari cannot), and distinguishes denied permission, missing microphone and oversized recordings. Turn notices (timeout, retry, send failure) render above the composer, where the user is looking; a hard stop and terminal states stay at the top because they replace the conversation. A finished session shows its closing card with one primary action ("Wróć do panelu"), the deep link "Otwórz zapis" beside it, an optional `SessionSummaryPanel` for reading a single-session summary, and the boundaries line once, under the card; new follow-ups prepare cumulative avatar memory automatically. `/privacy` and `session-copy.ts` must describe that automatic behavior. On a phone the session header stays one row (compact timer, a hairline progress bar under it, "Pomoc" always visible) and the boundaries line collapses to one tappable line; starter prompts show until the user's **first message**, not until the transcript is empty — a session starts with the avatar's opening message, so the old emptiness check hid them forever. **Phones:** this is the only fixed-height screen (`h-[100dvh]`), and three rules hold it together: `main` is `relative overflow-hidden` (the `sr-only` helpers are `position: absolute`; without a positioned ancestor they escape the clip, stretch the document and let the whole conversation be dragged upward, leaving a blank strip); the viewport meta carries `interactive-widget=resizes-content`, with `useVisualViewportBox` as the Safari/WebView fallback, so the composer stays above the on-screen keyboard; and nothing tall lives inline in the `shrink-0` header — the crisis panel is an absolutely positioned overlay with its own scroll, and once the conversation is over the whole column scrolls (`SessionMessages` `variant="finished"`) instead of squeezing the transcript under the closing card.
- **`/dashboard/avatar`** only picks a perspective. It carries no history; the save bar can save the choice or save and request a start on the dashboard. All five are shown side by side as voice cards — the `voiceSample` from the catalog is the thing that actually helps someone choose, so it is on every card at once rather than one at a time; Approach descriptions and `pairingNote` sit in a collapsed disclosure on each card; short UI labels live in `perspective-copy.ts`, independently of the AI prompts. The save bar renders only after a real change (a `<noscript>` copy covers users without JS), so hydration causes no layout shift. Avatar art is 256 px WebP (`public/avatars/*.webp`, a few KB each; `src/lib/__tests__/modalities-assets.test.ts` pins the files) — do not reintroduce the 185 KB PNGs.
- **`AppHeader`** has no nav tabs. The logo returns to the dashboard, an active conversation surfaces as a contextual pill (`session-flow/active-session-badge`, read **across all avatars** — a conversation started under another perspective must still have a way back), and the account menu holds account + sign-out. The admin entry lives on the account page, behind `getAdminContext`; `AdminShell` carries its own "back to panel" + sign-out because it has no `AppHeader`.
- **Dead ends are bugs.** Every terminal state must say what to do next: the exhausted free allowance links to `/account/billing` when sandbox purchases are enabled, or explains manual premium and links the support contact while billing is off; `/account` redirects to `/account/security` (plan + allowance + password + privacy link); `/account/blocked` redirects active accounts back to the dashboard and shows the contact plus subscription-management and deletion links; `404` keeps the header. `SiteFooter` (privacy/terms page `/privacy`, contact, and a disclaimer that points to "your local emergency number" rather than a country-specific one) sits on every non-session page — the session page stays full-height and already shows boundaries + crisis help. Copy for plan/allowance lives in `session-flow/plan-copy.ts`, session length in `session-flow/session-budget.ts` (derive the minutes from `resolveSessionDurationSeconds(plan)` — never hard-code them, and never assume 15: a premium account is told 60), the support address in `support-contact.ts` (`DEFAULT_SUPPORT_EMAIL` = the official mailbox, `SUPPORT_EMAIL` env overrides it; an invalid override falls back to the default, so the contact CTA is always present).
- **Wording:** in English the user picks a **perspective** (the avatar is its face), talks in a **conversation** (never "session" on screen), and every screen says once that SafeSpace is an "educational conversation simulation". In Polish the user picks a **perspektywa** (the avatar is the face of it). Use "perspektywa" for the choice and "awatar" only for the persona; on screen it is always a **rozmowa**, never a "sesja" ("Zakończ rozmowę", "Rozmowa zakończona", "Czas rozmowy minął" — `sesja` stays in code and API names). Where the avatar is known, say it by first name ("Lena uwzględni wasze wcześniejsze rozmowy", "Zobacz, co Lena pamięta") rather than "pamięć awatara". The first-run card on `/dashboard` shows the two-step path (choose perspective → start) and `?avatar=updated` confirms the saved choice. Each screen carries the "edukacyjna symulacja rozmowy" disclaimer **once**: the footer on ordinary pages, the line under the composer in a conversation, the line under the closing card afterwards — the dashboard card and the help block do not repeat it.
- **Shapes:** two button shapes only — a pill (`rounded-full`, 44 px) for inline and secondary actions, and `rounded-[14px]` (48 px, full card width where it is the main step) for primary block buttons and inputs; cards are `rounded-[20px]`, insets inside cards `rounded-2xl`. Account, 404, blocked and delete pages follow the same radii as the dashboard.

### `src/lib/` subsystems and their boundaries

Several directories carry a `README.md` that is the **authoritative contract** — read it before touching the code. The boundaries are a privacy design, not just style:

- **`session-data/`** — owner-bound repository over private tables (`therapy_sessions`, `session_messages`, `session_summaries`, `session_trial_claims`, the people-card and topic-map tables). Entry point `getSessionDataContext()`. Free-trial start _must_ go through `claimFreeTrialSession()` (DB unique constraint, not a UI check); the free-plan session cap is read through `readSessionQuota()` (`quota.ts`) and enforced by a DB trigger (see "Account plans" above). Deletes go through `deleteOwnedSession()` (hard-deletes content, leaves a content-free tombstone). `SessionHistoryListItem.summaryState` is read for a whole page in one query by `listOwnedSessionSummaryStates()` over `SUMMARY_STATE_SELECT` — a select that deliberately omits `summary_text`, so the list can mark an available summary without holding its text; a failed read degrades to no markers rather than failing the history. Hand-maintained domain types in `types.ts` are the privacy contract — see its README before adding Supabase typegen.
- **`session-safety/`** — `evaluateSessionSafety()`; the configured AI classifier maps `normal|caution|crisis` → `allow|allow_with_constraints|hard_stop`. Fail-closed. Crisis resources for PL/US + local fallback.
- **`session-ai/`** — `generateSessionResponse()`, prompt + copy + shared request profiles. Provider selection in `ai-provider/env.ts`, factory in `provider.ts`.
- **`session-summary/`** — generates optional single-session summaries and cumulative avatar memory; both are user-visible.
- **`session-transcription/`** — voice-message transcription via OpenAI or OpenRouter (`transcribeSessionAudio()`, provider abstraction like `session-ai`); backs `POST /api/session/transcribe`. Audio is conversation content — same privacy rules apply.
- **`session-flow/`** — pure-ish state machines, request/response contracts, persistence, markdown rendering, time-limit math (the orchestration glue used by routes).
- **`operational-visibility/`** — **the only sanctioned logging path.** Emit via `logOperationalEvent()` + builders in `session-events.ts`; never `console.log`. Allowlist-driven sanitizer. Permitted fields only: `requestId`, `outcome`, `durationMs`, `provider`, `riskState`, `action`, `reasonCode`, optional `userHash`, and the token counters `inputUnits` / `outputUnits` (named that way on purpose — the denylist rejects any field containing `token` or `prompt`). **Never** log message/prompt/content/summary/email/token/provider payloads/`modalityId`/`avatarId`/raw `user.id`/the UI locale. Route paths are logged with identifier segments replaced by `:id`. Transcription provider failures log `session.transcription_failed` (category only, never audio). Read hosted logs with `npx wrangler tail --name safespace`.
- **`admin/`** — admin auth, account access/block, account plan (free/premium grant + revoke, audited), and **content-free aggregates only** (status, duration bucket, trial marker, plan, dates — never conversation text). Surfaces: `src/pages/admin/`, `src/pages/api/admin/`. Admin identity lives in the `admin_users` table; there is no runtime service-role key and no endpoint to create the first admin — it's provisioned by owner-run SQL (snippet in README "Admin setup").
- **`billing/`** — sandbox-only Checkout, Portal, signed webhooks, owner billing status and the cancellation gate before account deletion. A dedicated PostgreSQL role can access billing data but never conversation content; see its README.
- **`modalities.ts`** — modality + avatar catalog; `getValidAvatarChoice()` validates a stored choice. Each entry carries two prompt fields: `sessionStyleHint` (the full avatar persona — voice, what it listens for, opening move, advice stance, session arc, reply shapes, `Avoid:`) used only by `session-ai`, and the short `summaryLensHint` used only by `session-summary`. Do not feed the full style hint to the summary path: a summary needs the modality lens, not conversational rules, and the oversized hint used to overflow that prompt budget and silently truncate its own `Avoid:` tail. Prompt-budget caps for both are asserted in tests — keep hints under the editorial budget rather than raising the cap.

### AI providers: OpenAI and OpenRouter

`AI_PROVIDER=openai` selects direct OpenAI by default; `openrouter` restores the existing router. Both use the current `OPENROUTER_*MODEL` and effort variables, with separate `OPENAI_API_KEY` and `OPENROUTER_API_KEY`. All entry points use the configured provider, including safety, lenses, summaries, memories and transcription. There is no automatic cross-provider fallback. See `src/lib/ai-provider/README.md` for the transport, local configuration and retention boundaries. OpenAI uses `store: false`; this does not establish account-level ZDR or preserve OpenRouter's Azure EU routing.

Three directories share the work: `ai-provider/` selects the provider (`getAiProviderName()` in `env.ts`: unset → `openai`, any other value **throws** `invalid_ai_provider_configuration` rather than routing private data elsewhere) and dispatches through `sendAiChat()` (`chat.ts`); `openai/` is the Chat Completions transport plus `resolveOpenAiModel()` (`model.ts`: strips the `openai/` prefix and rejects any other vendor prefix or an OpenRouter `:variant` suffix such as `:batch`); `openrouter/` keeps the SDK transport, `privacy.ts` routing and the env defaults. The `*WithOpenRouter` exports pin OpenRouter explicitly; the main factories follow the configured provider. On OpenAI, Luna does not accept `minimal`, so the adapter maps it to `low` and raises the classifier budget from 256 to 1024 tokens. In production the provider is the `AI_PROVIDER` entry in `wrangler.jsonc` `vars` (declared `access: "secret"` in the Astro schema, but not a secret); `scripts/write-production-secrets.mjs` reads it from there, requires the matching GitHub secret before migrations, rejects an `sk-or-` key as `OPENAI_API_KEY`, and never prints values. `wrangler.jsonc` deliberately has **no** `secrets.required`: Wrangler would filter local secrets outside that list, and the required key depends on the provider. `ai-provider/__tests__/deployment-secrets.test.ts` pins that script; `provider-routing.test.ts` walks every pipeline (conversation, opening, safety, summary, memory, people/topics, lens, transcription) through both providers with a fake network. `config-status.ts` names the selected provider's key in the dev-time missing-config banner.

The base `openai/gpt-5.6-luna` model prefers the exact `azure/eu` endpoint via `getOpenRouterPrivateProviderPreferences(model)` in `openrouter/privacy.ts`. Its default Azure route returned repeated upstream 429s while the EU endpoint completed the same synthetic safety and session requests. Keep fallbacks enabled and preserve `dataCollection: "deny"`, `requireParameters: true`, and `zdr: true`; provider preference is not permission to relax privacy. Safety, session and summary builders share this routing. Other model variants retain default routing until verified separately.

The OpenRouter alternative uses `@openrouter/sdk` (`src/lib/openrouter/sdk-chat.ts`). Four models, set by env: `OPENROUTER_SAFETY_MODEL` (classifier), `OPENROUTER_SESSION_MODEL` (responses, incl. reasoning-model support), `OPENROUTER_SUMMARY_MODEL` (summaries; falls back to the session model), `OPENROUTER_TRANSCRIPTION_MODEL` (voice input); plus `OPENROUTER_SESSION_REASONING_EFFORT` (`minimal|low|medium|high|xhigh`, session responses only — overrides the per-model default effort in `session-ai/openrouter-request-params.ts`; `high`/`xhigh` also switch to a larger completion budget and a longer timeout in `openrouter-session-response.ts`, an invalid value is ignored); all optional — in-code defaults live in `src/lib/openrouter/env.ts` and the safety classifier.

**Token budgets and reasoning models.** Reasoning models bill hidden thinking against the same completion budget as the visible answer, and they think before writing — too small a budget returns `finish_reason: "length"`, which both session and summary parsers reject as `invalid_provider_response` (so do `content_filter` and `tool_calls` finishes). `resolveSummaryMaxCompletionTokens` (`session-summary/openrouter-summary.ts`) and `resolveSessionMaxCompletionTokens` (`session-ai/openrouter-session-response.ts`) list these models per-branch and **must be updated together** — a model added to one but not the other silently breaks that path (this is exactly how Gemini 3.7 Flash summaries failed). The whole GPT-5.6 Luna family (`isOpenRouterGpt56LunaModel`, base/`-pro`/`:batch`) is pinned to `medium` reasoning for sessions and `low` for summaries with a 2 400-token base cap on both. Automatic cumulative memory uses at least 4 000 tokens to accommodate its larger summary. `src/lib/openrouter/__tests__/deployed-model-budgets.test.ts` runs the models from `wrangler.jsonc` through every request builder (session, summary, people/topic extraction, safety classifier, lens labeller), so a deployed model without a budget branch fails CI instead of production — when you switch a model, that test is the checklist.

## Conventions

- **Path alias** `@/*` → `./src/*` (tsconfig + vitest both configured).
- **Astro components** for static layout; **React islands** only for interactivity. No Next.js directives (`"use client"`). Extract hooks under `src/components/hooks/`. Hydration is deliberate per island: `client:load` only for the live session and for the history when a `?session=` deep link must open a preview; native-POST forms (auth, avatar choice, password) are `client:idle`; the dashboard history is `client:visible`.
- **Theme and motion**: the `dark:` variant in `global.css` matches both the explicit `[data-theme="dark"]` and the system preference (`prefers-color-scheme` guarded by `:root:not([data-theme="light"])`), and a global `prefers-reduced-motion` rule shortens every animation/transition — no per-component opt-outs.
- **Pages parallelise independent reads** (`Promise.all` in `dashboard.astro`) — do not reintroduce a chain of dependent `await`s for reads that only share the user.
- **Tailwind**: merge classes with `cn()` from `@/lib/utils` — never concatenate class strings.
- **shadcn/ui** in `src/components/ui/` ("new-york", base color neutral, lucide icons). Add via `npx shadcn@latest add [name]`.
- **Validate API input with hand-written type guards / contract modules** (zod is NOT a dependency — e.g. `session-flow/message-contract.ts`, `parseSessionIdParam`, `auth-validation.ts`); return stable domain error codes, never raw Supabase `message`/`details`/`hint` to UI, logs, or response bodies.
- **Tests** live in `__tests__/` next to code (`src/lib/**`, `src/components/**`, `src/pages/**`); `.test.ts` / `.test.tsx`. Vitest `environment: "node"`.
- **Shared types** (entities, DTOs) in `src/types.ts`; subsystem-local domain types stay in that subsystem's `types.ts`.

## Migrations & data

`supabase/migrations/`, naming `YYYYMMDDHHmmss_short_description.sql`. **Always enable RLS on new tables with granular per-operation, per-role policies.** Private session tables and admin operation functions are defined here. Local stack: `npx supabase start` (Docker). There is no break-glass admin content access — any legal/safety exception needs a separate audited plan, not an implicit helper.

CI applies migrations _before_ publishing code inside one locked `deploy` job, so every migration must be backward-compatible with the currently deployed code (expand/contract: add before you remove). Multi-step owner-bound writes live in `security invoker` SQL functions, including `claim_free_trial_session`, `delete_owned_session` and `complete_session_message_turn`. RLS still applies. `schema-drift.test.ts` checks domain/SQL constants; `npm run test:db` also executes every migration and verifies real ownership and concurrent-write behavior. The `20260904204248` migration enforces lifecycle transitions, guards direct legacy content inserts with the parent lock, and purges private turn receipts on deletion.

**Grants: revoke first.** Supabase's default privileges give `anon`/`authenticated` ALL on every new table in `public`, so a column-level `grant` only narrows anything after a table-level `revoke all privileges ... from anon, authenticated` (`20260901120000` does this for every private table and `schema-drift.test.ts` pins the list). A new table must follow the same pattern or the column list is decorative. Three database gates now back what the app assumes about a session row: `therapy_sessions_enforce_budget` (SQLSTATE `P0006`) freezes `started_at`/`expires_at`/`duration_bucket_seconds` once a row leaves `created`, rejects `expires_at` beyond `started_at + bucket`, and keeps a free account's bucket at the free budget — only a _change_ is judged, so a premium revoke never cuts a session under way; `therapy_sessions_purge_on_tombstone` deletes messages and summaries whenever a row becomes `deleted`, whichever path set the status; `admin_audit_events.target_user_id` is nullable with `on delete set null`, so an account can be deleted after it was ever blocked or granted premium. There is still **no retention job**: transcripts of finished sessions live until the owner deletes them, which is a product decision (window length) that has not been made yet.

### Self-service account deletion

`/account/security` links to `/account/delete`, a server-rendered confirmation form requiring `USUWAM`.
The deletion page and `POST /api/auth/delete-account` require authentication but allow blocked accounts to erase
their data. The endpoint requires a same-origin request and calls `delete_own_account` with the caller's SSR client.
The public RPC is a security-invoker wrapper around a private security-definer function with an empty search path,
explicit grants and `auth.uid()` ownership; it accepts no target user id. One Auth user deletion cascades through
all account data and Auth sessions. Both audit actor and target references become null while events remain.
Existing access JWTs are stateless, but the middleware's `getUser()` rejects a deleted user and foreign keys prevent
recreating owner data. The endpoint clears browser Auth cookies even if post-deletion sign-out fails.
With billing data present, account deletion first durably blocks purchases, resolves pending checkout attempts and
confirms immediate cancellation in Stripe. The deletion RPC refuses to bypass this gate; Stripe failure preserves
the account and permits a retry. Accounts without billing data still delete while billing is off. There are no
automatic refunds. Apply the additive account-deletion and billing migrations before publishing the corresponding
Worker code; only local sandbox operation requires the additional billing settings below.

Public/optional: `OPENROUTER_SAFETY_MODEL`, `OPENROUTER_SESSION_MODEL`, `OPENROUTER_SUMMARY_MODEL`, `OPENROUTER_TRANSCRIPTION_MODEL`, `OPERATIONAL_LOG_HASH_SECRET` (enables stable `userHash` correlation; absence does not block requests or fall back to raw `user.id`), `SUPPORT_EMAIL` (optional override of the public contact address `safespacenow123@gmail.com` — `support-contact.ts` — shown in the footer, on the blocked-account page, and as the premium CTA), `PEOPLE_MEMORY_MODE` (`off|on`, people cards; anything else means `off`, read only through `session-flow/people-memory-mode.ts`), `SESSION_LENS_MODE` (`off|on`, thematic lenses; read only through `session-flow/session-lens-mode.ts`), `TOPIC_MAP_MODE` (`off|on`, topic map; read only through `session-flow/topic-map-mode.ts`). All declared in `astro.config.mjs` `env.schema`. Build-time only: `SITE_URL` — when set, enables Astro `site` + the sitemap integration (deliberately off until the final domain is chosen).
- Local: `.env` (Node tooling) / `.dev.vars` (Cloudflare local dev, gitignored). Copy from `.env.example`. When `.dev.vars` exists, Wrangler uses it instead of `.env`; restart the dev server after changing either. In production every public var (`AI_PROVIDER`, the three feature flags, `BILLING_MODE`, the `OPENROUTER_*` model and effort settings) lives in the `vars` block of `wrangler.jsonc` — versioned and reviewable, kept in sync with `.env.example`; only secrets go through GitHub Secrets and `scripts/write-production-secrets.mjs`.
- Optional billing settings: `BILLING_MODE=off|sandbox`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_ID`, `BILLING_APP_URL`, `BILLING_DATABASE_URL`. Local sandbox uses `.dev.vars.billing` through `npm run dev:billing`; it must also contain local Supabase settings and the selected AI provider key when testing conversations. Do not add local sandbox keys to deployment secrets.
- Product/architecture docs in `context/foundation/` (`prd.md` holds the privacy guardrails; also `roadmap.md`, `tech-stack.md`, `infrastructure.md`, `test-plan.md`, `shape-notes.md`) and `context/deployment/deploy-plan.md`. `context/changes/<feature>/` holds the per-feature plan/change/verification folders written by the 10xDevs toolkit (`AGENTS.md`, `.agents/skills/`); do not create them from roadmap output. `docs/idea.md` and `docs/case.md` are the original Polish product notes.
